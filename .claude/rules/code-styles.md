## Рекомендации по языку C# и стилю 

### **Современный синтаксис**
- Первичные конструкторы (primary constructors) — предпочтительны для хендлеров и сервисов.
- File-scoped namespaces.
- Глобальные `using` выносятся в `GlobalUsing.cs` соответствующего проекта.
- Примечание: в новом коде (`*.Web`) file-scoped namespaces обязательны; в существующих `*.Domain` / `*.Infrastructure` исторически блочные namespace — переводить их при правке файла не требуется.

### **Безопасность нулевых значений**
- Разрешены ссылочные типы, допускающие значение null (`<Nullable>enable</Nullable>`). 
- Не используй `!` для подавления предупреждений, если это не задокументировано.
- Исключение (принятый в проекте паттерн): `= null!;` для обязательных строковых свойств сущностей и ViewModel.

### **Неизменяемость**
- `Request`-типы CQRS — `record` (как в шаблоне).
- Для новых самостоятельных DTO и доменных событий — `record` / `readonly record struct`.
- ViewModel остаются изменяемыми `class` (наследуются от `ViewModelBase`, заполняются рукописным маппингом) — это осознанное исключение, не переводить в `record`.

### **Стиль написания кода**
- Используй `var` для локальных переменных, когда тип очевиден из правой части выражения.
- Применяй `nameof()` вместо строковых литералов для именования методов, свойств и событий если это возможно.
- Применяй `is` и `as` вместо приведения типов.
- Используй `switch` выражения вместо `switch` операторов, когда это возможно.
- Используй `switch` выражения вместо цепочек `if-else`, когда это возможно.
- Не используй `try-catch` для управления потоком выполнения. Ожидаемые ошибки возвращай через `Operation`/`Result` (см. раздел «Обработка ошибок»), `try-catch` — только для действительно исключительных ситуаций (пример из шаблона: `TransactionBehavior` ловит любое исключение, откатывает транзакцию и пробрасывает его дальше).
- Объявляй методы и свойства как `private` по умолчанию, если они не предназначены для использования вне класса.
- Явно указывай модификаторы доступа для всех членов класса, чтобы избежать неявной видимости.
- Помечай классы как `sealed` по умолчанию, если они не предназначены для наследования.
- Публичную бизнес-логику (хендлеры, сервисы) желательно покрывать тестами — правила см. в `testing.md`. Тест-проекта в репозитории пока нет.

### **Асинхронный поток**
- Добавляй `Async` к именам собственных асинхронных методов (методы, реализующие сторонние интерфейсы, — напр. `Handle` из `Mediator` — переименовывать нельзя).
- `ConfigureAwait(false)` в ASP.NET Core не нужен (нет `SynchronizationContext`); добавляй только в переиспользуемых библиотеках вне ASP.NET Core.
- Всегда передавай `CancellationToken` в асинхронные вызовы, включая `SaveChangesAsync(token)`. В текущем коде это соблюдается не везде — при правке файла доводи до конца.
- Добавляй `CancellationToken` в конструкторы классов, которые выполняют асинхронные операции, чтобы обеспечить возможность отмены операций при необходимости.

### **Обработка ошибок**
- Используй подход Fail Fast.
- Используй шаблон `Result` вместо генерации исключений для ожидаемых потоков бизнес-логики. Пакет — `Calabonga.Results` (namespace `Calabonga.OperationResults`, тип `Operation<TModel, TError>`); `Operation.Result(...)` при успехе, `Operation.Error("...")` при ошибке.

### **Правила работы с базой данных**
- Используй `Calabonga.UnitOfWork` для работы с базой данных, чтобы обеспечить единый подход к транзакциям и обработке ошибок.
- Используй `unitOfWork.GetRepository<TEntity>()` для получения репозитория сущности, а затем вызывай `unitOfWork.SaveChangesAsync()` для сохранения изменений.
- Используй `unitOfWork.Result` для проверки успешности операций с базой данных.
- Передавай `CancellationToken` в методы работы с базой данных, чтобы обеспечить возможность отмены операций при необходимости.
- Используй `async/await` для всех операций с базой данных, чтобы избежать блокировки потоков и улучшить производительность приложения.
- Используй `Calabonga.OperationResults.Operation<TModel, TError>` для возврата результатов операций с базой данных, чтобы обеспечить единый подход к обработке ошибок и успешных результатов.
- Не бросай исключения для ожидаемых ошибок при работе с базой данных, вместо этого используй `Operation.Error("...")` для возврата ошибок.
- Не используй `DbContext` напрямую в коде приложения, вместо этого используй `Calabonga.UnitOfWork` для обеспечения единообразного подхода к работе с базой данных.

### **Время/Часы**
- Цель: внедрять и использовать `TimeProvider` вместо прямого вызова `DateTime.UtcNow`. Сейчас в шаблоне используется `DateTime.UtcNow` напрямую и `TimeProvider` не зарегистрирован — в новом коде внедряй `TimeProvider`.
- Желательно использовать `DateTimeOffset` вместо `DateTime` для временных меток (в текущих сущностях, напр. `EventItem.CreatedAt`, — `DateTime`).
